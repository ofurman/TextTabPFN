Can a task story help TabPFN-2.5 predict from few labels?

Text-conditioned thinking rows: two iterations of controlled experiments on synthetic causal scenes

Runs: 2026-11-10 to 2026-11-12 on one Apple M4 Pro (PyTorch MPS). Software: tabpfn 9.2.0 with the frozen TabPFN-2.5 classifier checkpoint. Branch thinking-rows.

Results
  • One pooled vector for the whole story did not help. This result holds for MiniLM and for the larger bge-base encoder. Different stories give almost the same vector (cosine about 0.99).
  • One token per feature role helped. The story arm beat its control by 0.004 to 0.010 nats at n = 8 to 32. This result holds on the held-out scene families. Corrupted roles made the predictions worse.
  • Story-guided preprocessing still beats every trained adapter at n ≤ 32. At large n, it makes the predictions worse.
  • We trained each adapter once. The confidence intervals do not include training-run variance. A same-adapter check confirms the 4000-step role-token result.

1. Question

TabPFN-2.5 learns from a small labeled table in context. A table often comes with a text that describes its setting. We ask two questions. Does one shared story per dataset improve predictions from few labels? How does the benefit change when the number of labels grows?

The story arm and its control get the same labeled rows, the same feature schema and the same target definition. Only the story arm gets the story. We test the improvement as a hypothesis. We do not assume it.

2. Setup

Synthetic scenes with known ground truth

Each scene is a random structural causal model. It has 6 to 15 numeric features and a binary target y. Each feature has one hidden role:

  • Markov blanket: the feature causes y, or y causes the feature.
  • Irrelevant: the feature has no causal path to y.
  • Noisy measurement: the feature is one of 2 or 3 noisy readings of one hidden cause of y.

Six families combine three mechanisms (linear, tanh, interaction) with two noise types (Gaussian, heavy-tailed). Families 0 to 3 train the adapters. Families 4 and 5 (interaction mechanism) are the held-out test set. All verdicts use only families 4 and 5. Feature names are neutral (x1 to xp), so the names give no hint.

Fair comparison and statistics

  • Control arm: the same architecture, budget, episodes and learning rate. It reads only the schema or neutral tokens. Story arm minus control arm isolates the value of the story content. Generic tuning of the thinking rows helps both arms equally.
  • Evaluation: 200 held-out scenes. Support sizes n = 8 to 1024. Five nested support draws per scene. 512 fixed query rows. All arms score the same rows.
  • Metric: the paired per-scene difference in query log loss, with a 95% scene-bootstrap CI (1000 resamples).
  • Verdict rule D-08: we fixed this rule before the first result. The rule gives supported if at least two of n = 8, 16, 32 have a CI upper bound below 0. It gives harmful if one of these n has a CI lower bound above 0. Otherwise it gives not supported.

3. How the methods work

This section uses one real held-out scene as the example: family 4, seed 2000000. It has 9 features. The code paths are in src/texttabpfn/. The code blocks below are short versions of the real code. Names such as seeded_init stand for longer code.

3.1 TabPFN-2.5 thinking rows

TabPFN-2.5 embeds each table cell as a 192-dimensional vector. Before the transformer layers, it puts 64 learned “thinking rows” in front of the labeled rows. Every column gets the same 64 vectors. All labeled rows and query rows can attend to them. Our methods change only these 64 rows. TabPFN-2.5 itself stays frozen.

# tabpfn/architectures/tabpfn_v2_5.py, AddThinkingRows.forward (native)
# x_BRiCE: (batch, rows, columns, 192) embedded cells
thinking_rows_BTCE = (
    self.row_token_values_TE          # (64, 192) learned in pretraining
    .unsqueeze(0).unsqueeze(2)
    .expand(batch_size, -1, num_features, -1)   # same rows in every column
)
x_BRCE = torch.cat([thinking_rows_BTCE, x_BRiCE], dim=1)
single_eval_pos += self.num_thinking_rows

Our adapters keep the same input and output contract. During a forward pass, we put the adapter in place of model.add_thinking_rows. After the pass, we restore the native module.

3.2 The story

The schema text depends only on the number of features. The story adds structural facts. It gives no coefficients, signs, equations or noise levels. For the example scene, the encoder input of the story arm is:

Schema (the control arm reads only this text)Columns: x1, x2, x3, x4, x5, x6, x7, x8 and x9 are 9 numeric features, listed in column order. Each row is one record. The target y is a binary outcome with value 0 or 1.
Story (the story arm reads schema + newline + story)Known structure: x7 directly influences y. x8 is directly influenced by y. x1, x3 and x9 are noisy measurements of one hidden quantity that influences y. x2, x4 and x6 are noisy measurements of a second hidden quantity that influences y. x5 is unrelated to y.

The true roles in this scene: x7 is a parent of y and x8 is a child of y. Group A (x1, x3, x9) and group B (x2, x4, x6) measure two hidden causes. x5 is irrelevant. The longest text over all scenes has 159 MiniLM tokens.

The corruption tests change the story text. The omitted variant removes the story. The irrelevant variant uses the story of another scene. The wrong variant permutes the roles among the features.

3.3 Iteration 1 and bge arm: pooled story vector

A frozen sentence encoder turns the full text into one vector e. MiniLM (all-MiniLM-L6-v2) gives a mean-pooled, L2-normalized 384-d vector. bge-base-en-v1.5 gives a 768-d CLS vector. A learned matrix P (384 × 768) maps it to 384-d. Each thinking row i gets its own shift Wi·e. W starts at zero, so the untrained adapter gives exactly the native output.

# src/texttabpfn/adapter.py, TextConditionedThinkingRows
self.theta_TE  = checkpoint_rows(model)                 # (64, 192), frozen buffer
self.weight_TED = nn.Parameter(torch.zeros(64, 192, 384))  # W, starts at 0

def rows(self):                                           # e: (b, 384) text embedding
    shift_bTE = torch.einsum("ted,bd->bte", self.weight_TED, self._text_bD)
    return self.theta_TE[None] + shift_bTE                # (b, 64, 192)

def forward(self, x_BRiCE, single_eval_pos):              # same contract as native
    rows_BTCE = self.rows()[:, :, None].expand(B, -1, C, -1)
    return torch.cat([rows_BTCE, x_BRiCE], dim=1), single_eval_pos + 64

# use: swap the module in for one forward pass, then restore it
e = MiniLM.encode(schema + "\n" + story)                 # (384,), mean-pooled, L2-normalized
with conditioned(model, adapter, e):                      # model.add_thinking_rows = adapter
    logits = binary_logits(model, x_support, y_support, x_query)

Trainable parameters: 4,718,592 for MiniLM (W only). bge adds P, for a total of 5,013,504.

3.4 Iteration 2: per-feature role tokens

Each feature gets one short sentence that states only its role. The sentence does not name the feature. The slot position carries the column identity. Features with the same role get the same token.

MiniLM encodes each sentence on its own. A shared matrix P maps each 384-d token to 25 dimensions. We concatenate the 15 slots into one 375-d vector s. Then each thinking row gets the shift Wi·s.

# src/texttabpfn/role_tokens.py, RoleTokenThinkingRows
sentences = role_sentences(scene.describe()["roles"])   # 9 strings, column order
tokens = slot_tokens(MiniLM, sentences)                   # (15, 384), rows 10..15 = 0

self.projection_PD = nn.Parameter(seeded_init(25, 384))   # P, same start in both arms
self.weight_TES = nn.Parameter(torch.zeros(64, 192, 15 * 25))  # W, starts at 0

def summary(self):                                        # s = concat_j(P t_j): (b, 375)
    return torch.einsum("pd,bsd->bsp", self.projection_PD, self._text_bD).flatten(1)

def rows(self):
    shift_bTE = torch.einsum("tes,bs->bte", self.weight_TES, self.summary())
    return self.theta_TE[None] + shift_bTE                # forward() as in iteration 1

The roles come from an exact parse of the template story (Scene.describe()). This test shows if TabPFN can use clean structure. It does not test free-text understanding.

3.5 Story-guided preprocessing (no training)

This baseline uses the same roles to edit the table before native TabPFN reads it:

  1. Remove each feature that the story calls unrelated. In the example, remove x5.
  2. Keep each Markov-blanket feature. In the example, keep x7 and x8.
  3. For each measurement group, standardize its columns and replace them with the first principal component. Align the sign to the first column of the group. In the example, A (x1, x3, x9) becomes one column and B (x2, x4, x6) becomes one column.

The example table goes from 9 columns to 4. The PCA uses no labels. The main variant fits on support and query features. A second variant fits on support features only.

3.6 Training

Both arms train in lockstep on the same stream of synthetic episodes. Each episode draws one training scene, a support size n, the support rows and 512 query rows. The loss is the mean cross-entropy on the query rows. Only W (and P) get gradients.

# src/texttabpfn/training.py (role_training.py and followon.py use the same loop)
for step in range(4000):
    for k in range(8):                                    # 8 episodes per step
        ep = make_episode(settings, index)                # same episode for both arms
        # ep: one training scene (families 0 to 3), n ~ log-uniform(8, 1024),
        #     stratified support rows, 512 separate query rows, texts per arm
        for arm in ("story", "control"):
            logits = episode_logits(model, adapters[arm], text_input[arm], ep)
            loss = F.cross_entropy(logits.reshape(-1, 2), y_query.reshape(-1))
            (loss / 8).backward()                         # gradient reaches W (and P) only
    adam_step(lr=1e-3, warmup=100, cosine_to=0.1 * lr)
    if step % 250 == 0:
        dev_loss(64 dev scenes, n in (8, 32, 128))        # keep the best checkpoint

In iteration 1 and the bge arm, the story arm sees a mix of texts: 75% correct story, 15% no story, 10% one wrong fact. The role-token story arm always gets the correct roles. Each run selects its checkpoint by dev loss only. The dev scenes come from families 0 to 3.

The channel is large. A perfect map from text to rows could lower the log loss by 0.16 nats at n = 8. Per-column rows add only 25 to 35%, so we kept shared rows.

Held-out result (stages 2 to 5)

Both adapters beat native TabPFN by up to 0.012 nats at n = 16. The control arm got the same gain. On held-out families, story minus control was −0.0008, +0.0001 and +0.0012 at n = 8, 16 and 32. The verdict was “harmful”, by about 0.001 nats.

The corruption tests agree. A missing story cost +0.0015 at n = 8. The story of another scene and permuted roles had no measurable effect. So the adapter detected if a story was present, but it did not use the content.

A diagnostic shows the cause. Stories with the same number of features had a MiniLM cosine of 0.989. The role information was only a small part of the vector.

8. Conclusions and limits

What the data shows
  • A frozen TabPFN-2.5 can use story structure through its thinking rows when each feature gets its own role token.
  • One pooled sentence vector loses the role information. This result holds for a small encoder and for a larger one.
  • The benefit is largest with few labels. It gets smaller as the number of labels grows.
  • Wrong or irrelevant roles make the role-token adapter worse.
What the data does not show
  • Free-text understanding. The roles come from an exact parse of template stories.
  • Robustness to the training seed. We trained each arm once. The bootstrap covers scenes, not training runs. A same-adapter check confirms only the 4000-step role-token result.
  • Results in the ensembled TabPFN sklearn wrapper or on real datasets. We did not measure label savings (H2).
  • Corruption results for the 10k arms and the bge arm.

Next steps

  1. Train each arm with 2 or 3 seeds. Then the verdicts include training-run variance.
  2. Use a local LLM to get the roles from free or paraphrased stories. Feed the roles as role tokens.
  3. Test per-column thinking rows that bind each column to its own role token.
